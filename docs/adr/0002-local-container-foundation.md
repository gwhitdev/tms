# ADR 0002 — Local foundation and independent installer

Status: M02-T01 implementation candidate.

The business API and worker use .NET 10, PostgreSQL and the React web client. The initial deployment target is this computer's Linux-container Docker engine. Use one foundation Compose project and a separate installer project. All server components and infrastructure are containerised; mobile device runtimes remain later native-capable clients.

The infrastructure control agent uses Node's HTTP/filesystem/process APIs and the pinned Docker CLI. It serves the React setup UI, persists control state outside PostgreSQL and executes only predefined Compose build/install/status operations against the included release. The user cannot supply commands, project names, images, paths or mounts. Only this local operator agent mounts the Docker socket. That access is a privileged host boundary: compromise of the agent can compromise the engine. The TMS API, worker, gateway and storage do not mount the socket. Production control-plane hardening, signed releases, separate agent identities, TLS and scoped upgrade/recovery operations are M09 acceptance work.

Installer access binds to `127.0.0.1:8740`. It checks exact Host/Origin, JSON shape, typed nonprivileged ports and CSRF. A local one-use code creates an HttpOnly SameSite=Strict session with a server-enforced thirty-day expiry; local operator reset revokes it. This is infrastructure access, independent of future TMS tenant/system identity. API keys and service passwords never pass through the UI. Service secrets are distinct, generated cryptographically in dedicated volumes, and mounted read-only only to their required consumers. PostgreSQL bootstrap has administrator access to initial role secrets; migration, API and worker each receive only their own credential volume. Engine/operator access remains trusted.

The database bootstrap creates `tms_migrator`, `tms_api` and `tms_worker` without superuser, BYPASSRLS, role/database creation, inherited migrator membership or runtime schema ownership. The migrator owns only the foundation schema. Runtime grants permit readiness, heartbeat and a controlled diagnostic retention marker. There are no tenant tables yet; actual adversarial tenant isolation, pooled-context and API tests are M02-T02.

Use supported pinned release versions and immutable base-image digests in Dockerfiles/manifests: .NET SDK10.0.400/runtime10.0.12, PostgreSQL18.6, SeaweedFS4.48, Node24.19.0, Docker CLI29.7.2 and nginx1.30. Microsoft lists10.0.12 as the current .NET10 patch on 2 October 2026; final review corrected the earlier runtime image pin before task verification. Frontend and Npgsql dependencies have exact versions and lockfiles; NuGet auditing and pnpm release-age checks remain enabled. Selected images were inspected/pulled before acceptance. Future updates require a tested image/dependency change.

Readiness requires the current migration checksum, a restricted runtime role and reachable internal storage; worker readiness additionally requires a current database heartbeat. Gateway health forwards the API result. The installer reports actual Compose service health independently of the application database. Data persists in declared database/storage volumes across container recreation. Storage's S3 credential config is private; the internal filer fixture in tests is not a tenant-authorised POD endpoint.

The local profile has neither high availability nor an agreed production RPO/RTO. UK parcels and launch volumes inform the first workload, but peak load, growth, operator, certificates, availability, identity provider and recovery targets remain owned decisions. No routing, GPS, ERP or live parcel data is processed by this increment.

Primary references: [Microsoft .NET support policy](https://dotnet.microsoft.com/en-us/platform/support/policy/dotnet-core) identifies the current runtime patch and servicing requirement; [Docker startup dependencies](https://docs.docker.com/compose/how-tos/startup-order/) describe readiness ordering; [PostgreSQL image](https://hub.docker.com/_/postgres) documents bootstrap and storage layout; [SeaweedFS 4.48 release](https://github.com/seaweedfs/seaweedfs/releases/tag/4.48) identifies the selected storage release; [Npgsql10 release notes](https://www.npgsql.org/doc/release-notes/10.0.html) support the pinned PostgreSQL driver family. The topology and trust boundaries are our implementation decisions.
